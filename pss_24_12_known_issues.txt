#PSSKPL-5061
New in R24.6.0
In an NE where loadtype = partial, if a new extension shelf is added and the extension shelf
is equipped with a power filter (PF) that is not already part of the feature list, the PF RPM
will not be downloaded from the remote server and the PF will report a “SWUNAVAIL -
Unable to fetch SW from server” alarm.
Workaround: To clear the SWUNAVAIL alarms and download the necessary PF RPM,
perform a manual update:
1. Type config software dynamic featurelist add <softwareLoadEntities,
softwareLoadEntities> and <Enter>.
Where <softwareLoadEntities> is one or more software entities in the form of a comma
separated list; the softwareLoadEntities names relate to card-names.
2. Type config software dynamic update external and <Enter>.
Result: The added <softwareLoadEntities> are downloaded to the NE.

#PSSKPL-293
If the NE initiates a FTP file transfer request to a remote file system server (for example:
OTDR, PM, UAL, DB backup/restore, software audit/download) and the FTP protocol is
blocked by a firewall between the NE and the remote file system server or the provided

servers.

11DPE12, 11DPE12A, and 11DPE12E support a single priority level/CoS for user traffic.
Internally the software implements a prioritization scheme that assigns in-profile (<CIR)
traffic, co-called “green” frames, into a high priority queue and out-of-profile traffic (<PIR but
>CIR), so-called “yellow” frames into a lower priority queue. A SP (strict priority) based
scheduling algorithm is used to prioritize green/in-profile traffic. It is strictly internal and not
visible to the operator. This prioritization is proprietary since according to IEEE 802.1Q
standards, green and yellow traffic for the same CoS should always be mapped to the
same queue; then - within a queue - color is used to determine which packet to drop first in
case of congestion. However as a result of this proprietary prioritization, there exists a
potential for mis-ordering for a given conversation/flow.
Workaround: To prevent mis-ordering, it is recommended to use strict policing with CIR =
PIR (EIR = 0), thereby avoiding existence of yellow packets.

New in R23.12.0
During a software upgrade, if a backout is performed on a node that includes coupled 1830

After the SWC1 cards are alarm free, clear INTTSIFAIL on SWC2 (SWC# represents SWC2).
